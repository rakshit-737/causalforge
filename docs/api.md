# CausalForge API

The current API exposes the deterministic investigation engine for local fixture use. It is
tenant-scoped and requires the local development principal headers:

```text
X-Tenant-ID: <tenant UUID>
X-User-ID: <user subject>
```

The pair is verified against the local `tenants`/`users` tables. The header adapter is deliberately
not production authentication; production mode remains disabled until a real identity provider and
token verification layer are implemented.

## Endpoints

### Health

```text
GET /health/live
GET /health/ready
```

Readiness fails closed when migrations are missing or a required dependency is unavailable.

### Events

```text
POST /api/v1/events
POST /api/v1/events/batch
GET  /api/v1/events/{event_id}
```

Batch requests are bounded to 100 events. Payloads are normalized, redacted, deduplicated, stored
as evidence, and passed through deterministic detection. The response contains counts and detection
summaries; raw payloads are never returned.

### Incidents

```text
POST /api/v1/incidents
GET  /api/v1/incidents
GET  /api/v1/incidents/{incident_id}
POST /api/v1/incidents/{incident_id}/investigations
GET  /api/v1/incidents/{incident_id}/timeline
GET  /api/v1/incidents/{incident_id}/claims
GET  /api/v1/incidents/{incident_id}/evidence
GET  /api/v1/incidents/{incident_id}/graph
GET  /api/v1/incidents/{incident_id}/hypotheses
GET  /api/v1/incidents/{incident_id}/response-plans
POST /api/v1/incidents/{incident_id}/hypotheses
GET  /api/v1/incidents/{incident_id}/hypotheses
POST /api/v1/incidents/{incident_id}/hypotheses/{hypothesis_id}/verify
GET  /api/v1/incidents/{incident_id}/hypotheses/{hypothesis_id}/verifications
```

Claims expose evidence IDs and explicit states. The current API does not promote claims to
`verified` or execute response actions. Hypotheses are persisted as `proposed` until a separate
verification request evaluates integrity-checked case evidence. Verification requires two
independent source families and complete coverage by default; deadline or evidence-budget failures
return explicit `insufficient_evidence` rather than best-effort support. Each attempt is persisted
with its evidence IDs, source families, policy, and unmet requirements.

## Example local flow

After applying migrations and creating a local user row:

```bash
curl -H "X-Tenant-ID: <tenant-uuid>" -H "X-User-ID: analyst" \
  -H "Content-Type: application/json" \
  -d '{"title":"fixture incident"}' \
  http://127.0.0.1:8000/api/v1/incidents
```

Use the returned incident ID as `case_id` for `/api/v1/events/batch`. The OpenAPI document at
`/docs` is generated by FastAPI and is the authoritative request/response schema.

## Safety behavior

- Missing or invalid local principal: `401`.
- Cross-tenant resource lookup: `404` without cross-tenant disclosure.
- Tenant mismatch inside an event payload: `422` and no committed records.
- Malformed canonical event: `422` with a generic safe detail.
- Foreign incident or hypothesis lookup: `404` without cross-tenant disclosure.
- Insufficient verification coverage, source independence, deadline, or budget: `201` with a
  durable `insufficient_evidence` decision, not a promoted conclusion.
- No arbitrary shell, target connector, write action, or LLM tool is exposed by these endpoints.
